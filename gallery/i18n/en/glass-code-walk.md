title: A glass-material code block pops in and 10 lines settle one by one; the camera pushes to 1.68x and then walks the code "read a line → glide to the next" (a floating-point line number linePosition drives both camera and highlight band, so the band glides between lines rather than snapping), non-current lines dimmed to 0.30; when finished, a 0.85s pull back to the wide shot lifts the dimming
usage: Walking the viewer through a short piece of real code/config in narration — tech tutorials, code explainers, open-source project introductions, "these few lines are the key" moments; 6~10 lines where every line deserves its own spoken sentence
---

## Intent
Narrating code has two dead zones: paste a full screen of code and the viewer's eyes have nowhere to land — you're on line 5 while they're still reading line 1;
paste only the two key lines and the viewer can't see the structure they live in. This card is the solution — **the whole block is present, but only one line is lit at a time**.
The viewer's gaze is towed by that highlight band and the pace is yours; the surrounding lines are dimmed but not gone, so the sense of structure never leaves.

There are three vital constraints. **First, the floating-point line number**: `linePosition` is a float, and both camera and highlight band are computed from it live,
so walking from line 2 to line 4 it runs continuously through 2.0 → 4.0 and the band **glides** between lines.
A highlight that jumps cell by cell is "a program switching classes"; the glide is "an eye moving".
**Second, dwell-based rather than constant-speed**: each line dwells `dwell` then glides `stepDur` to the next. A constant-speed conveyor reads as "the code auto-playing" —
viewers wait for it to finish instead of listening to you; the dwell pattern is "I've finished this sentence — next line".
**Third, close on the wide shot**: after following 8 sentences the viewer holds only fragments and needs one look at the whole passage.
Pull back to `zoom = 1` while lifting the dimming — from "read this line" back to "read the whole structure"; skip this beat and the telling isn't finished.

The glass block itself is **a means, not an end**: the semi-transparent dark base is what makes syntax colors work (on light glass every token color smears into chalk),
and the backdrop blur kneads whatever is behind it — inside and outside the block you can see two states of the same background, the only visible proof of "glass".

**Original source visuals (user-finalized 2026-08-25: abandon the adaptation, implement the remocn source as-is)**: every visual value of the glass block
copies `glass-code-block` 1:1 — `rgba(10,10,10,0.6)` glass base + `blur(16px)`, 1px gradient stroke,
`0 50px 120px rgba(0,0,0,.55)` shadow, 40px chrome + true-color macOS traffic lights (`opacity .6`) + `#a1a1aa` title,
28px gutter `#3f3f46`, five token colors (`#e4e4e7` / `#52525b` / `#86efac` / `#c4b5fd` / `#fcd34d`).
The stage backdrop also reproduces the source's `previewBackdrop` (a warm-brown→ink-green dark photo `/bg.jpg`) — the demo bans external resources,
so a CSS gradient recreates that image's tonal distribution. This also dissolves the adaptation's problem of faking a glass backdrop with "three grayscale soft blobs":
**the source always had a dark photo background — the glass has something real to blur.**

## Motion Core
- Two structural layers: `.camera` (a world-coordinate layer filling the stage, `transform-origin: 0 0`, the card's only transformed element) → the glass block (fixed in world coordinates). Only the camera, the highlight band, and per-line opacity move
- **`transform-origin: 0 0` is the precondition for the inverse solve**. The default `center` makes `scale` pivot around the element's center and the formula breaks
- **The core inverse solve**: `tx = W/2 − zoom·cx`, `ty = H/2 − zoom·cy`, `scale = zoom`. Meaning: "move the anchor's post-scale position to frame center"
- **The anchor's vertical position comes from floating-point line interpolation**: `linePosition` is continuous between adjacent lines (`lo = floor(p)`, `hi = lo+1`, blend the two line centers linearly by `p − lo`).
  Line centers are measured live from the DOM (`rowTop[i] + rowH[i]/2`) — font-size changes, line-count changes, and half-height empty lines all track automatically, no hand-filled coordinates
- **Horizontally always the block center, never following characters**: code is read **by whole lines**. This is the first dividing line from [cursor-locked-zoom](cursor-locked-zoom.md) (which locks x to the character cursor)
- **Highlight band and camera share one source**: the band's `top`/`height` are interpolated from the same `linePosition` (`trackedRow()` returns y / top / h in one call).
  Shared source ⇒ only one timeline advances and the two cannot desynchronize. Give the band its own tween to "chase" the camera and any duration change pulls them apart
- **Dimming is a continuous quantity, not binary**: `near = max(0, 1 − |i − linePosition|)` — the further from the current line, the darker.
  When the band sits between two lines, both are **half-lit at once**, and that beat reads as "moving"; binary switching (only integer lines lit) degrades the "glide" into a "flicker"
- **The walk stops only on lines with content**: an empty line is layout, not a sentence; the `stops` array filters empties. But the interpolation still passes through them (`linePosition` is continuous), so the band sweeps smoothly across an empty line
- **Dwell-based rhythm**: `dwell 0.32s` pause + `stepDur 0.26s` glide (`power2.inOut` — settled at both ends; one "line hop" is an event with a beginning and an end)
- **Boundary clamping (a required patch for the white stage; the source lacks it)**: `halfWidth = W/(2·zoom)`, `cx = clamp(cx, blockLeft + halfWidth, blockRight − halfWidth)`, likewise vertically; when the asset is smaller than the viewport it degrades to centering.
  **The block must be wider than the visible width at walk focal length** (960 / 1.68 ≈ 571px, hence the demo's 600px) — otherwise horizontal clamping degrades to centering and thin strips of white stage show at the frame's sides
- **The ending tweens only two values, `zoom` and `dimAmt`**: `zoom` shrinks ⇒ the visible rectangle grows ⇒ the clamp range narrows ⇒ the center is continuously squeezed back to the block's middle; at `zoom = 1` the block is smaller than the frame, the clamp degrades to centering ⇒ landing exactly on a centered wide shot. No second displacement tween
- Two entrance beats: block `y 16→0` + `scale 0.965→1` (`back.out(1.3)` slight overshoot), with the fade-in on an **independent time window** (displacement moves first, opacity follows — the remocn-wide entrance idiom); then lines settle `y 6→0` + fade at 0.08s per line (source `staggerFrames 10` frames ≈ 0.33s; this card tightens to 0.08s — 10 lines lay out in 1.0s, not eating narration time)
- **Lines must be block, not flex**: a flex container drops whitespace-only anonymous children ⇒ inter-token spaces and leading indentation all vanish (`export function` collapses to `exportfunction`). A pitfall hit in practice
- Syntax color uses only four anchors (keyword purple `#c4b5fd` / string green `#86efac` / number yellow `#fcd34d` / comment gray `#52525b`, plain code `#e4e4e7`), a minimal regex tokenizer, not a real highlighter (not part of this card's motion, but the values are locked to the source's `TOKEN_COLORS`)
- **Font size is back-solved from block width, not an aesthetic choice**: block width 600 is the floor at `zoom 1.68` (960/1.68 ≈ 571 + margin); usable text width = 600 − 2×24 padding − 28 gutter = 524px; monospace char width ≈ 0.6em ⇒ with the longest line at 49 characters, `fs ≤ 17.8`, so **17px** (line height 26 = round(17×1.55), empty line 14 = 17×0.8). The source is 880 wide @18px; this card's block is 280px narrower, so **the font must shrink with it, or line ends spill outside the block** (hit in practice: at 18px the import line's closing quote was clipped outside the block)

## Parameters
| Parameter | Typical value | Tuning feel |
|------|--------|----------|
| `zoom` | 1.68 (range 1.5~1.8) | Walk focal length. **The whole line must fit inside the frame** — the hard divide between "walking" and deep-zoom; >2 line ends get clipped and viewers read half sentences; <1.4 the zoom does nothing and the dimming works alone |
| `dwell` | 0.32s | Per-line dwell (the time to read this line). Set by narration pace — glide away only after he finishes the sentence; <0.2s viewers get dragged off before registering it, >0.6s the band looks stuck |
| `stepDur` | 0.26s | Inter-line glide. <0.15s reads as cell-snapping (the float interpolation wasted), >0.45s every hop makes you wait — 8 sentences accumulate an extra 1.5s |
| `dimFloor` | 0.30 | Dim floor for non-current lines. 0 = only one line visible (all structure lost — might as well paste just that line); >0.55 the walk is invisible |
| Line count | 6~10 lines | <5 lines doesn't need a walk (one screen reads fine — give the wide shot + one [slow-push-in](slow-push-in.md)); >12 lines the walk exceeds 8s and viewers drift |
| Line width vs font size | See above | **Changing block width/focal length/line width — any one — requires recomputing font size via `usable text width ÷ (longest line chars × 0.6)`** — this card's only hard coupling |
| Line width | ≤ 49 characters | The cap for a 600px block @17px monospace (see the back-solve above); wrapping makes line heights uneven and the line-center interpolation hiccups |
| `pushDur` | 0.55s | Wide → walk-focal push-in (dimming and band appear with it). <0.3s reads as a hard cut, >0.9s viewers wait for it to finish |
| `holdEnd` | 0.30s | Dwell after the last line. Gives "that sentence is done" its punctuation; 0 = yanked away the instant reading ends |
| `pullDur` | 0.85s | Pull to wide. <0.5s reads as "snapping back"; >1.2s viewers expect another destination |
| `lineIn` | 0.08s | Per-line entrance interval. >0.15s laying out 10 lines takes 1.5s of dead narration; 0 = the whole block lights at once and the "lines settling" beat is gone |
| Block backdrop blur | 16px (source value) | The glass's backdrop blur. <8px the glass reads as a "translucent color slab"; >26px the background behind blurs into uniform gray and the glass feel itself disappears |

## Known Pitfalls
- **The font-size vs block-width formula** (field addition 2026-08-27): give that "hard coupling" line a formula —
  `fontSize ≤ (blockWidth − horizontal padding) ÷ zoom ÷ (longest line chars × 0.6)`, and **CJK characters count as 1.0, not 0.6**
  (lines with CJK comments are often the longest). Measured: a 900px block / zoom 1.6 / 21px clips a 44-character import line outside the block.
- **The highlight band switching classes by integer line number** — cell-by-cell jumps read as "a program switching styles", not "an eye moving". Float line number + interpolation is this card's defining feature.
- **Giving the band its own tween to chase the camera** — they desynchronize on any duration change. Band and camera must be computed live from the same `linePosition`.
- **Binary dimming** (only the current integer line lit) — during the 0.26s glide the frame "flickers" instead of "moving"; dimming must be the continuous quantity `1 − |i − linePosition|`.
- **Constant-speed sweep across all lines** (no dwell) — reads as "the code auto-playing"; viewers wait it out instead of listening. The dwell pattern is "I've finished this sentence".
- **`transform-origin` left at the default `center`** — the inverse solve breaks, every camera position wrong (in a "looks like a bug but you can't say where" way). Must be `0 0`.
- **Raw inverse solve without boundary clamping** — at the first/last line the frame gets pushed outside the block; on a white stage that's a sweep of blank. The source's dark background hid it; a port must add this.
- **Block narrower than the visible width at walk focal length** (960/zoom) — horizontal clamping degrades to centering and thin white edges show permanently, reading as "the asset vanished". Back-solve block width from `960/zoom + margin`.
- **Lines with `display: flex`** — flex drops whitespace-only anonymous children; inter-token spaces and indentation all vanish (`export function` → `exportfunction`). Lines must be block + `white-space: pre`.
- **Light glass (translucent white) holding code** — syntax colors all smear into chalk on a light base; all four anchor colors dead. The glass block's interior must be dark.
- **Nothing behind the glass** (a plain white stage) — the backdrop blur has nothing to knead; "glass" degrades into a "translucent gray slab". There must be a blurable dark background behind the block (the source uses a photo; this card an equivalent CSS gradient).
- **Block narrowed but font kept at the source's 18px** — the longest line's tail gets clipped outside the block (hit in this card's build). Font size and block width are hard-coupled; recompute via the back-solve.
- **The walk stopping on an empty line** — an empty line is layout, not a sentence; stopped there, the viewer doesn't know what they're looking at. `stops` must filter empties (while the interpolation still passes through them).
- **Ending without the wide shot** — the viewer holds only fragments, never the whole passage. The walk must close on the full picture, **lifting the dimming at the same time** (pulling only the focal length leaves the wide shot dark — no full picture delivered).
- **Using it on 30 lines of code** — the walk balloons past 20s. Over 12 lines, either crop to the key passage or switch to [evidence-scroll-tour](evidence-scroll-tour.md) for a scrolled browse.
- Writing lorem or pseudocode — viewers spot it as fake instantly, and the persuasive weight of "this is real code" zeroes out; write short realistic code (the kind that would compile).

## Reuse Guide
- HTML/GSAP: `demos/glass-code-walk/index.html`. **To change the code, edit only `CONFIG.code`** — tokenizing, line building, line centers, `stops` (empty-line filtering), and walk sentence count all follow automatically; no coordinates or timestamps to patch by hand.
  Rhythm in `CONFIG.dwell` / `stepDur` / `pushDur` / `pullDur`; focal length `CONFIG.zoom` (after changing it, re-check block width against `960/zoom`); dim depth `CONFIG.dimFloor`; block geometry `blkL/blkT/blkW/blkH` (used both to derive line centers and as the camera's clamp boundary; update the CSS `.ring` to match).
  Liftable core: `CONFIG` + `trackedRow()` + `apply()` (inverse solve + clamping + band + dimming, twenty-odd lines).
- Minimal asset-swap flow: ① fill the asset's four edges into `blkL/blkT/blkW/blkH`; ② write "the current item's top / height / center y" as a function evaluated by floating-point index (not necessarily code lines — list items, table rows, checklist entries all work); ③ touch nothing else. **As long as you can write the one function "item p's world coordinates", this card can walk it.**
- Remotion port (this is the source): `registry/remocn/glass-code-walk/index.tsx` (130 lines) + `registry/remocn/glass-code-block/index.tsx` (tokenizer + glass-block visuals + per-line `Sequence`).
  **The visuals are copied 1:1** (user-finalized 2026-08-25: use the source's original visuals) — even the sample code is the source's `DEFAULT_CODE`;
  porting back to Remotion, use `<GlassCodeBlock>` directly for the visuals and replace only the walk segment.
  The source's `linePosition = interpolate(frame, [0, scanEnd], [0, lineCount − 1])` is a **constant-speed sweep across all lines** (empties included);
  this card changes it to "dwell-based + stop only on content lines" — the single most worthwhile change in a port (a constant-speed scan feels like a machine scanning, not a person reading).
  Seconds ↔ frames (30fps): source `staggerFrames 10` = 0.33s/line (this card 0.08s), `PULL_BACK_FRAMES 24` = 0.80s (this card 0.85s), `durationInFrames 150` = 5.0s, default `zoom 2.6` is the deep-zoom tier (this card's walk tier takes 1.68).
  The source's `ANCHOR_SCREEN_X 110` pins the anchor at **110px from the frame's left** rather than center (paired with deep-zoom); this card's walk tier switches to "horizontally always the block center".
  The source computes line centers via `lineHeightOf(line)` (empty `fontSize×0.8`, normal `fontSize×1.55`); this card measures equivalently from the DOM.
  The camera layer uses `translate` + `scale` + `transformOrigin: "0 0"` (identical to the source); add the boundary clamping when porting.
- Editing-software equivalents: AE — render the code block as an image/precomp, add a Null as the "current line anchor" with **position keyframes** to the reading rhythm (one per line, Easy Ease both sides), bind the camera or layer position to the expression `W/2 − zoom × null.position[1]`; the highlight band is a rectangle shape layer with its position bound to the same Null (making it and the camera natively same-source); dimming via an inverse-masked black adjustment layer whose opacity follows the Null.
  JianYing — manual approximation only: enlarge the code block and lay position keyframes to the reading rhythm + a white translucent block as the highlight band with the identical keyframes (the two keyframe runs must align frame-by-frame or band and camera drift apart), and dimming can only be a global brightness drop, not per-line; **not recommended for many lines**.
  Premiere — same via `Motion`'s Position/Scale keyframes, the band as a Graphic layer. In any software, "band and camera must share a source" is enforced by **driving both from one anchor**.
- Sound: one `tick` per line hop during the walk (`vol` 0.30, `rate` alternating within 0.96~1.14 — a repeated sample must vary pitch or it reads as a mechanical loop); one `whoosh` on the block pop-in (`vol` 0.34, `rate` 1.05); one `lowpad` under the push-in (`vol` 0.22, `dur` 0.6, `rate` 0.9) to seat the focal change; one `whoosh` on the pull to wide (`vol` 0.30, `dur` 0.8, `rate` 0.86 — falling pitch = closing). **The dwell is silent** — the pause belongs to the narration, not the sound design.
  Cue times derive from line count: `pushAt = leadIn + (lineCount−1)×lineIn + 0.26 + 0.10`, hop k = `pushAt + pushDur + dwell + (k−1)×(dwell + stepDur)`, pull = last hop + `stepDur + holdEnd`. **Changing the line count means recomputing this chain** (at 10 lines: 1.40 / hops from 2.27 every 0.58 / pull at 6.89).

## Scope
- Belongs to this card: the defining discipline that **the floating-point line number `linePosition` drives both camera and highlight band** (shared source ⇒ desync impossible); the "glides rather than snaps" behavior from inter-line linear interpolation (`lo`/`hi`/`p − lo` blend of line centers); the **dwell-based rhythm** (`dwell` pause + `stepDur 0.26s` `power2.inOut` glide, not a constant conveyor); the trade-off of **horizontally always the block center, never following characters** (code is read by whole lines); the **continuous** dimming formula (`1 − |i − linePosition|`, with both neighbors half-lit while the band is between lines); stopping only on content lines while the interpolation still passes through empties; the inverse solve `tx = W/2 − zoom·cx` (with `transform-origin: 0 0` as precondition); the boundary clamping caging the visible rectangle inside the block's edges (plus the freebie of "tween only zoom and dimAmt; displacement follows from the clamp"); the 1.5~1.8x walk focal band and the acceptance rule "the whole line must fit in frame"; the closing beat of **pulling to zoom=1 while lifting the dimming**; the block entrance's "displacement first + independent fade window" offset; the 0.08s per-line settling stagger; and the hard coupling "font size back-solved from block width" (changing block width/focal length/line width all require recomputing the font size, or line ends spill).
- Does not belong to this card: the demo's sample code content (= the source's `DEFAULT_CODE`), the `scene.tsx` filename, the specific 600×440 geometry and 17px font size (but the **coupling between them** belongs to the card), the band's radius and 3px left accent bar rendering, and the "code" subject matter itself (list items, table rows, checklist entries walk equally well).
  **Note: the glass block's visuals and token palette are not "our design" but the remocn source verbatim** (`rgba(10,10,10,0.6)` + `blur(16px)`, 1px gradient stroke, `0 50px 120px` shadow, 40px chrome + true-color macOS traffic lights, `#a1a1aa` title, 28px gutter `#3f3f46`, the five `TOKEN_COLORS`, the dark photo backdrop) — the user finalized on 2026-08-25 to follow the source's original visuals, so reuse **copies this whole set**; do not re-adapt (an earlier adaptation with `rgba(22,22,28,.74)` + 18px blur + grayscale traffic lights + four self-picked colors + three grayscale soft blobs has been retired).
- Migration interfaces: `CONFIG.code` is the sole migration entry — swap in the 6~10 lines you actually narrate, and tokenizing/lines/centers/empty-filtering/sentence count all recompute (but **a changed line count means recomputing the sfx cue chain**, formula in the Reuse Guide; **a longer longest-line means recomputing font size** via the back-solve); set `dwell` to the narration pace (glide only after he finishes the sentence — don't let the band outrun the explanation); validate `zoom` by "are line ends clipped while walking" (not by composition) — **the whole line in frame is the hard standard**; a changed `zoom` requires re-checking block width against `960/zoom + margin`, then recomputing font size from block width; set `dimFloor` by "can the surrounding lines still show structure"; an asset swap only rewrites the one function "item p's world coordinates"; for vertical, block width to 92% of frame width, line width under 28 characters, `zoom` down to 1.4 (vertical type is large — 1.68 clips line ends).
- Background requirements: **the source's original visuals = the content itself; user-finalized 2026-08-25: implement the remocn source as-is**.
  The stage base is a **dark backdrop** (the source's `previewBackdrop` is a warm-brown→ink-green photo `/bg.jpg`; the demo bans external resources and recreates its tonal distribution with a CSS gradient),
  **exempt from the "white-stage neutrality" constraint**. Both reasons are hard: ① the glass block's interior must be dark — syntax colors live on the dark base (on light glass all four anchors smear into chalk);
  ② **there must be something blurable behind the block** — against pure white the backdrop blur has no material to knead, "glass" degrades into a "translucent gray slab", and the card's signature material is gone.
  Landing on live footage/dark frames, the stage base can simply become that footage (better than the CSS gradient — real material kneaded by the glass makes the inside/outside contrast clearer);
  on a light background this card does not hold — use a non-glass code block instead (the highlight-band walk mechanism itself is material-independent and can be lifted alone).
- Division of labor with neighboring cards: **vs [cursor-locked-zoom](cursor-locked-zoom.md) (the other tier of the same mechanism)** — the two share the same inverse solve and the "camera driven by content progress" discipline, but at different tiers: that card is 2.6~2.8x **deep-zoom following the cursor** (x locked to the character, seven-eight characters per screen, the target moving **character by character**), this card is 1.5~1.8x **line-by-line highlight walking** (x locked to block center, whole lines legible, the target moving **line by line**) + glass block + dimming. **Shallow walk — this card; deep close-up — that card**: reading out one long command (horizontally long, single line) — that card; reading a multi-line passage (vertically long, one sentence per line) — this card. **vs [terminal-typing-log](terminal-typing-log.md)** — there the content moves (typed line by line + scrolling) and the camera doesn't; here the content is static (laid out once) while camera and highlight move. **vs [evidence-scroll-tour](evidence-scroll-tour.md)** — that card scrolls long material for browsing (high volume, not read sentence-by-sentence); this card walks short material sentence by sentence (low volume, every line spoken). **vs [focus-dim-spotlight](focus-dim-spotlight.md)** — that card dims to focus but **moves no camera and switches no focus** (one lock per use); this card's focus moves continuously; to emphasize a single spot, use that card.
